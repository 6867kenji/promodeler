# realitizer 分析と promodeler 設計方針

作成日: 2026-09-21
参照: https://github.com/koher/realitizer (commit 3c89cef, 2026-09-07 時点, Swift 約 10,500 行)

---

## 1. realitizer とは何か

RealityKit 向けの「コードファースト 3D アセット生成ライブラリ」。
Swift のソースコードそのものをモデルの唯一の正 (source of truth) とし、
エディタ操作の記録や .blend のような永続ドキュメントを一切持たない。

### 1.1 コンセプトの核

| 原則 | 内容 | 効果 |
| --- | --- | --- |
| Code-first | モデリング操作は合成可能な純粋関数。`MeshBuilder.box(...).beveled(...).unwrappingUV(...)` のように式として書く | Git で差分管理でき、レビュー・再現・パラメータ化が容易 |
| 決定性 | seed・品質プロファイル・バージョン付き JSON レシピで同一出力を保証。Swift の乱数ハッシュに依存しない | キャッシュ鍵化、テスト、LOD を「同じレシピを低品質で再評価」して生成できる |
| 明示的な契約 | 全操作が受理ドメインを文書化し、範囲外は黙って劣化させず throw する（例: bevel 幅はクランプしない、boolean は「ボクセル近似」と明記） | AI エージェントが「成功したつもり」になる幻覚を防ぐ |
| 段階パイプライン | ①形状 → ②表面仕上げ (法線/UV/頂点色/マテリアルスロット) → ③バインド (スキン/モーフ) → ④組立・アニメ | バインド後の処理は `MeshProcessingResult` で頂点対応を追跡し、スキンを壊さない |
| セマンティック ID | パーツ・ジョイント・ソケット・モーフ・クリップを文字列 ID で参照。頂点番号は契約にしない | 生成しなおしてもゲームコードが壊れない |
| AI エージェント前提 | `Skill/SKILL.md` 1 ファイルで API と手順を完結させ、Xcode MCP の RenderPreview で画像を見て反復 | 「コード編集 → 検証 → レンダ → 目視 → 修正」のループがエージェントの作業単位 |
| 検証の誠実さ | 「Ready ラベルはコンパイル成功の証明であり、GPU フレームが描けた証明ではない」と明記 | 視覚検証・数値検証・実機性能を混同しない |

### 1.2 機能範囲（実装済み）

- 形状: プリミティブ / 穴あき 2D プロファイル押出 / 回転体 / スイープ / ロフト / パラメトリック曲面 / 凸包 / SDF (marching tetrahedra)
- 形状処理: 位置溶接によるトポロジ再構築、面・辺の空間クエリ、領域押出、インセット、ソリッド化、メトリックベベル、面取り、Catmull-Clark
- 変形: ミラー、配列、bend / twist / taper、seed 付きノイズ変位
- 外観: 法線/接線、平面・円筒・球 UV 投影、自動 UV チャート+パッキング、頂点色、手続きテクスチャ、PBR/Unlit、透明モード
- リグ/アニメ: スキン、モーフ、ポーズ、クリップ、レイヤ付きアニメグラフ、ブレンド空間、IK/LookAt、ルートモーション、リターゲット
- ランタイム: RealityKit コンパイル、インスタンス、LOD、キャッシュ、GPU バッチ、物理、草・波エンバイロンメント
- プレビュー: コード指定のカメラ/ライト/表示モード（ワイヤ、法線、UV、ウェイト等）

### 1.3 「繊細でリアル」という観点での限界

realitizer は **ゲームアセット向けの中〜低ポリ・スタイライズド** を主眼にしており、
写実表現に必要な要素は薄い。ソースを読んだ限りの具体的な不足:

1. **テクスチャ生成が原始的**: `TextureImage.generate(sample:)` の per-pixel クロージャ、チェッカー、ホワイトノイズ（Perlin ですらない）、高さ関数からの法線マップのみ。fBm / Voronoi / ドメインワープ / トリプラナー投影なし。
2. **メッシュマップのベイクがない**: AO、曲率、キャビティ、厚み、ワールド法線などを焼く仕組みがない。写実的な「エッジの摩耗」「溝の汚れ」「上面の埃」はこれらをマスクにしたレイヤードマテリアルで作るのが定石であり、その基盤が丸ごと欠ける。
3. **マテリアルモデルが基本 PBR のみ**: baseColor / roughness / metallic / normal / emissive / opacity だけ。SSS、クリアコート、シーン、異方性、透過、変位なし。肌・布・塗装・ガラスの表現に届かない。
4. **ノイズ変位が単純**: `noiseDisplaced` は sin の積 1 オクターブ。多オクターブの微細ディテール（皮革のシボ、岩の凹凸）を作れない。ディスプレイスメントマップによる変位も、マルチレゾリューションも無い。
5. **ブーリアンがボクセル近似**: 精密なハードサーフェスの切り欠きには使えないと自ら明記。
6. **リメッシュ・デシメーションなし**: LOD は「同じレシピを低品質で再評価」のみ。スキャン的な高密度メッシュを扱えない。
7. **毛・布・散布**: 草と波は専用実装だが、汎用の毛髪カーブ・クロス・任意インスタンス散布はない。
8. **参照品質レンダラなし**: プレビューは RealityKit のリアルタイム描画。パストレーサ・HDRI ライティングでの確認ができないため、写実マテリアルの妥当性を判断しづらい。
9. **視覚検証が「人（またはエージェント）が画像を見る」だけ**: 多視点コンタクトシート、参照画像との定量比較、マニフォールド/自己交差/UV 重複の数値レポートがない。
10. **Apple 閉域**: Swift 6.3 / iOS 26 / macOS 26 前提。Windows で動かない。出力も RealityKit / .reality のみで glTF / USD / FBX 書き出しがない。

要約すると realitizer から学ぶべきは **「思想と契約設計」** であり、
**「写実性を担う中身（テクスチャ・マテリアル・微細形状・ライティング）」は別に用意する必要がある。**

## 2. Blender MCP だけでは不十分な理由

ユーザーの前提「MCP だけでは繊細な表現・テクスチャは困難」に同意する。理由:

- MCP の各ツール呼び出しは粗粒度（立方体追加、色設定）で 1 往復ずつ。シェーダーノード数十個・ベイク・散布を会話プロトコル越しに組むのはトークン効率も再現性も悪い。
- Blender セッションはステートフル。realitizer が禁じる「エディタ操作の記録」そのものになり、決定性と差分管理を失う。
- 失敗が黙って通る（bpy.ops の多くは文脈依存で、エラーにならずに何も起きない）。

ただし **Blender そのものは最強の写実カーネル** である。Geometry Nodes、シェーダーノード、
ベイク、Cycles、USD/glTF 書き出しを Python から完全に制御できる。
結論: **MCP ではなく、ヘッドレス Blender を「コンパイラのバックエンド」として使う。**

## 3. 言語とスタック（決定）

**Python を採用する。** Blender 同梱の Python 3.13（numpy 同梱）で動かす。

| 候補 | 評価 |
| --- | --- |
| Python + bpy (採用) | 写実に必要な機能（ノード、ベイク、Cycles、Geometry Nodes、USD）が既に工業品質で揃う。numpy でバルク頂点演算。LLM が最も正確に書ける言語 |
| Swift (realitizer 継続) | Apple 閉域。テクスチャ・ベイク・レンダラを自作する必要がある |
| Rust / C++ 自作カーネル | 高速だが、写実の中身（ノードシェーダ、ベイク、パストレーサ）を全部再発明することになる |
| TypeScript + three.js | プレビューは良いが、オフラインの高品質ベイク・ブーリアン・散布が弱い |
| Houdini | 手続きモデリングは最良だがライセンスと LLM の習熟度で不利 |

### 3.1 ローカル環境（計測済み）

| 項目 | 値 |

## 4. promodeler のアーキテクチャ

```
assets/<name>.py            <- 唯一の正 (Python でアセットを宣言)
        |  build
        v
promodeler.core   (純 Python / bpy 非依存)   定義型・検証・レシピ JSON・キャッシュ鍵
        |  compile
        v
promodeler.kernel (bpy, ヘッドレス Blender を毎回まっさらから起動)
   +- geometry   : bmesh ビルダー, モディファイア (bevel/subsurf/solidify/displace/boolean exact/remesh/decimate), Geometry Nodes
   +- detail     : 手続きテクスチャ駆動の変位, multires, ダメージ/歪みライブラリ, 毛髪カーブ, クロス凍結
   +- meshmaps   : AO / 曲率 / キャビティ / 厚み / 位置 / 法線 をベイク
   +- material   : ノードグラフ DSL, レイヤードマテリアル (マスク = メッシュマップ x 手続きノイズ)
   +- bake       : PBR テクスチャセット (basecolor/normal/rough/metal/AO/height) を任意解像度で焼く
   +- light/cam  : 固定 HDRI セット, ターンテーブル多視点, 診断パス (法線/AO/ワイヤ/UV チェッカ/クレイ)
   +- export     : glTF 2.0 / USD(Z) / FBX / .blend(キャッシュ), LOD, コリジョン, セマンティック名の保持
        |
        v
build/<name>/<hash>/   renders/*.png  report.json  model.glb  textures/*.png
        |
        v
promodeler.qa     数値 QA (非マニフォールド・自己交差・UV 重複・テクセル密度) + 視覚 QA (コンタクトシート, VLM 批評, 参照画像との距離)
        |
        v
Skill/SKILL.md    エージェント向け作業契約: 編集 -> build -> report/画像を読む -> 修正
```

### 4.1 realitizer から引き継ぐ設計原則

- ソースコードが唯一の正。`.blend` はビルド成果物・キャッシュに過ぎず、決して手で編集しない。
- 毎ビルドで Blender を `read_factory_settings(use_empty=True)` から起動し、状態を持ち越さない。
- パラメータは dataclass、seed と品質プロファイルを明示。乱数は全て seed 派生。
- 各操作の受理ドメインを文書化し、範囲外は例外。`bpy.ops` の「黙って何もしない」を kernel 層で必ず検出する。
- セマンティック ID（パーツ = Object 名、ソケット = Empty、リグ = Armature ボーン名）を書き出しまで保持。
- 段階パイプラインを守る: 形状 → 微細ディテール → UV → メッシュマップベイク → マテリアル → テクスチャベイク → リグ → 書き出し。

### 4.2 写実性を担う中核: レイヤードマテリアル

Substance Painter 流の定石をコードで再現する。これが realitizer に最も欠けている要素。

```python
mat = Material("worn_leather")
mat.base(Leather(color=srgb(0.32, 0.18, 0.10), grain_scale=180, seed=p.seed))
mat.layer(EdgeWear(strength=0.6), mask=Curvature(convex=True) * Noise(scale=40, detail=6))
mat.layer(Dust(color=srgb(0.7, 0.65, 0.6)), mask=WorldNormal.up * AO.inverted() * 0.4)
mat.layer(Dirt(), mask=Cavity() * Noise(scale=12, warp=0.3))
mat.layer(Scratches(density=0.2, seed=p.seed + 1), mask=Curvature(convex=True))
mat.finish(Principled(roughness_map=True, normal_map=True, sss=SSS(radius=(0.4, 0.2, 0.1))))
```

- マスクは **ベイク済みメッシュマップ**（AO / 曲率 / キャビティ / 厚み / 法線）と **手続きノイズ**（fBm, Voronoi, ドメインワープ）の積で作る。
- 投影は原則トリプラナー（Box 投影）で UV 継ぎ目を隠し、最終的に UV へ焼く。
- 出力は標準 PBR テクスチャセット。エンジン側は普通の glTF として読める。

### 4.3 微細形状（ディテール）

- 手続きテクスチャ駆動の Displace モディファイア（多オクターブ）で皮膚・岩・木目レベルの凹凸。
- Multires + 変位ベイクで、ローポリ + 法線/高さマップの構成にも落とせる。
- 「不完全さ」ライブラリ: 微小なゆがみ（Lattice/SimpleDeform）、エッジ欠け（boolean exact + 散布）、へこみ。均一すぎる CG 感を消す最重要要素。
- 毛髪・布: Curves オブジェクト、Cloth シミュレーションを固定フレームで凍結して形状化（決定性のため seed とフレームを固定）。
- Boolean は Blender の Exact ソルバ（Manifold）を使い、realitizer のボクセル近似の限界を超える。

### 4.4 検証ループ（エージェントの作業単位）

1. `promodeler build assets/boot.py` を実行。
2. `report.json` を読む: バウンディング、三角形数、非マニフォールド辺数、自己交差数、UV 重複率、テクセル密度、ベイク解像度、警告。
3. `renders/contact_sheet.png` を読む: 固定 HDRI の下で 6 視点 + 診断パス（クレイ、法線、AO、ワイヤ、UV チェッカ）。
4. 参照画像がある場合は VLM 批評（「靴の革らしく見えるか」）と定量距離（LPIPS / CLIP 類似度）を併記。
5. コードを直して 1 へ。

realitizer と同様「レンダが出た ≠ 正しい」を守る。数値 QA と視覚 QA を分けて報告する。

### 4.5 決定性とキャッシュ

- キャッシュ鍵 = hash(レシピ JSON + kernel バージョン + Blender バージョン + 外部入力のハッシュ)。
- Blender のノイズテクスチャは座標と seed で決定的。Cycles はサンプル seed 固定で決定的（ノイズはあるが再現する）。EEVEE は決定的。
- 外部画像（CC0 テクスチャ、AI 生成テクスチャ）を使う場合もハッシュで参照し、レシピに埋める。

## 5. realitizer に足りない要素（promodeler で追加するもの）

| 分類 | 追加要素 |
| --- | --- |
| テクスチャ | fBm / Voronoi / Musgrave / ドメインワープ、トリプラナー投影、画像入力、AI 生成テクスチャの取り込み |
| メッシュマップ | AO / 曲率 / キャビティ / 厚み / 位置 / ワールド法線のベイク |
| マテリアル | レイヤード（摩耗・埃・汚れ・傷）、SSS / クリアコート / シーン / 異方性 / 透過 / 変位、マテリアルプリセット集 |
| 微細形状 | 多オクターブ変位、Multires、不完全さライブラリ、Exact ブーリアン、リメッシュ、デシメーション LOD |
| 有機物 | 毛髪カーブ、クロス凍結、汎用散布（草だけでなく苔・石・ボルトなど） |
| ライティング/レンダ | HDRI セット、パストレーサ (Cycles)、ターンテーブル、診断パス |
| QA | 幾何数値レポート、コンタクトシート、VLM 批評、参照画像比較 |
| 書き出し | glTF / USD(Z) / FBX、PBR テクスチャセット、LOD、コリジョン、セマンティック名 |
| 移植性 | Windows / macOS / Linux、Unity / Unreal / three.js / RealityKit (USDZ 経由) |

realitizer から **引き継がない** もの: RealityKit ランタイム、アニメグラフ実行系、草・波の GPU 描画。
これらはエンジン側の責務とし、promodeler はアセット生成に集中する。
リグ・ポーズ・クリップの「定義」は保持して glTF アニメーションとして書き出す。

## 7. 主なリスクと対策

- **bpy の文脈依存 ops が黙って失敗する**: kernel では `bpy.ops` を避け `bmesh` / データ API を優先。使う場合は前後の状態差分で成功を検証する。
- **NVIDIA GPU がない**: Cycles は CPU / oneAPI。反復は EEVEE に限定し、Cycles は低サンプル + デノイズで最終確認のみ。
- **Blender のバージョン差**: 5.x の API 変更（`use_nodes` 非推奨など）を kernel 層に閉じ込め、core は bpy 非依存に保つ。
- **決定性の破れ**: クロス/物理はフレームと seed を固定し、結果メッシュをキャッシュに焼く。
- **エージェントのトークン消費**: report.json と 1 枚のコンタクトシートに集約し、フル解像度画像は要求時のみ読む。

## 8. 適用範囲の検討: 人型・空間・アニメーション

追記日: 2026-09-21。ヘッドレス Blender 5.1.2 で以下を実測済み:
Rigify 自動リグ生成（メタリグから 706 ボーン）、シェイプキーとキーフレームのコード生成、
ヘアカーブ (`CURVES`) 追加、Cloth モディファイア、glTF のスキン+モーフ+アニメーション書き出し。

### 8.1 人型モデル（条件付きで可能）

**結論: 素体をプリミティブから手続き生成する方式では写実的な人体は作れない。
「素体は外部のパラメトリック人体モデルから取り込み、それ以外をコードで生成する」ハイブリッドを採る。**

理由: 人間は顔の誤差に極端に敏感（不気味の谷）であり、解剖学的形状は規則で書き下せない。
realitizer もこの領域には踏み込んでいない。

| 要素 | 方針 |
| --- | --- |
| 素体 | **採用: Meta MHR (Momentum Human Rig, Apache 2.0)**。骨格スケールと体型係数を設計書の寸法にフィットさせ、`MeshFile`（sha256 付き）として取り込む（8.5）。候補だった MPFB は Blender アドオン依存、SMPL-X は研究用途制限があり見送り。特定人物の似姿はスキャン / 画像生成 3D をハッシュ参照の外部入力とする |
| 肌 | SSS + 曲率×ノイズによる毛穴・皺 + マイクロ法線。レイヤードマテリアル (4.2) をそのまま適用 |
| 髪 | ヘアカーブ + Geometry Nodes。seed 固定で決定的に生成 |
| 衣服 | クロス凍結（フレーム・seed 固定）または手続き裁断。装備・防具・ロボットは完全にコードファーストで高精細にできる |
| 表情 | シェイプキーをコード生成。ARKit 52 ブレンドシェイプ規約に合わせ、リップシンク・表情キャプチャと接続可能にする |

到達点: ゲームの AAA 級リアルを狙う。映画のデジタルダブルは狙わない。
アニメ調・ローポリ・ロボット・鎧はコードのみで高品質にできる。

### 8.2 空間・環境（得意領域）

建築と環境はもともと手続き的で、コードファーストが最も効く分野。Geometry Nodes はこの用途に設計されている。

- 壁・床・タイル・家具配列は規則、地形はノイズ、小石・植生は散布、汚れ・水染みはメッシュマップ由来のマスク。
- 現実感はマクロ（レイアウト）、メソ（小物のばらつき）、ミクロ（マテリアルの不完全さ）の三層で決まる。
- Cycles + HDRI で建築ビジュアライゼーション級の室内が作れる。
- 規模の制約: 部屋から街区までは問題ない。オープンワールドはストリーミングと LOD 階層が別途必要で、初期スコープ外。
- 再利用: 小物はキットバッシュ・ライブラリとしてレシピ参照し、シーンは glTF インスタンシング / USD で書き出す。

### 8.3 アニメーション（対応可能、realitizer より強い）

Blender は realitizer が自作していた機能をほぼ標準で持つ。

| 要素 | 方針 |
| --- | --- |
| リグ | Rigify のメタリグをコードで配置して自動生成。ボーン名を realitizer 流のセマンティック ID に対応付ける。自動ウェイトの上にコードで補正を重ねる |
| クリップ | ポーズを dataclass で書き、キーフレームや関数のベイクを F カーブに落とす（realitizer の `keyPoses` / `bake` 相当）。IK・LookAt・コンストレイントは標準機能 |
| モーキャプ | BVH / FBX 取り込みとリターゲットマップを自前で持つ（`RetargetMap` 相当） |
| 物理 | クロス・髪・剛体はシミュレーション後にキャッシュへ焼き、決定性を保つ |
| 書き出し | glTF（スキン+モーフ+ノード変換）、USD、FBX、Alembic |
| ランタイムグラフ | ステートマシン・ブレンドはエンジン側 (Unity / Unreal / three.js) に任せる。クリップとメタデータ（イベント、ルートモーションフラグ）のみ書き出す。realitizer が自作したのは RealityKit にグラフがなかったため |
| 検証 | キーフレームごとのコンタクトシートに加え、ボーン長保存・関節可動域・足滑りの数値チェックを report.json に入れる |

### 8.4 注意点

- Blender 5 系はアクションがレイヤー化され (`Action.layers`) API が変わっている。kernel 層で吸収し、core には露出させない。
- 写実的な肌・髪の最終的な見え方は書き出し先エンジンのシェーダに依存する。Cycles の見た目がそのまま出るわけではないので、エンジン別のマテリアル対応表を持つ。
- 人型は小物より工数が一桁大きい。ロードマップでは M5 以降に置き、M2 の写実マテリアルが完成してから着手する。

### 8.5 人体素体の実装: Meta MHR（2026-09-22 追記）

v0 のロフト素体（`assets/haruka.py` 初版）は寸法は合っても人体には見えず、設計書との差も
ヒップ −6.8 cm、股下 −7 cm 等と大きかった。Meta MHR に置き換えた。

- **MHR の構造**: 204 個のモデルパラメータ（関節角 + 名前付き骨格スケール `scale_spine_length`,
  `scale_shoulder_width`, `scale_uplegs`, `scale_lowlegs`, `scale_hip_width` ...）と 45 個の体型係数
  （体 20 / 頭 20 / 手 5）で、TorchScript (`mhr_model.pt`) が LOD1 18,439 頂点と 127 関節を出す。
  CPU で 1 回 0.09 s。`lod1.fbx` から UV・100 頂点グループのウェイト・126 ボーン階層を取る
  （`tools/mhr_dump_lod1.py`）。
- **フィット** (`promodeler/human/mhr.py`): 計測を微分可能に書く。身長 = 頂点 y の最大−最小、股下 =
  正中線の股の高さ、肩幅 = 左右 `uparm` 関節距離、足長 = 足の z 幅、頭高 = 頭頂 − `c_head`。
  周長は水平面とエッジの交点を角度順に結んだ折れ線長で、腕・手のウェイトが支配的な頂点を持つ
  エッジを除いて胴体だけを切る（背骨を縮めると肩が断面高さまで下がり腕を拾うため）。
  最適化は骨格スケール（長さ）→ 体型係数（周長）→ 骨格 → 体型の 4 段交互 Adam。両方同時だと
  周長の勾配が長さ項を圧倒して発散した。500 反復 35 s。結果は `build/human/<name>-<hash>/`
  にキャッシュ（targets と FIT_VERSION のハッシュ）。
- **取り込み**: `MeshFile(path)` 形状（レシピに sha256）、kernel は npz から頂点・三角形・UV を作り、
  ウェイトがあれば `skinned=True` 時に距離ウェイトの代わりに使う。`rig_from_file` で 126 関節の
  `Rig`。ポーズは MHR 関節名の world 空間回転。
- **結果** (05-woman): 身長 +1.8 mm、股下 −2.9 mm、肩幅 −0.1 mm、足長 +0.7 mm、頭高 +1.2 mm、
  バスト +1.9 mm、ウエスト −4.1 mm、ヒップ −10.8 mm、アンダーバスト +19.6 mm。バスト−アンダー差
  20 cm は 20 係数の表現力の限界に近い。ビルド 20 s、glb 3 MB、raise_arms / walk ポーズはツイスト
  ボーン込みで破綻なし。
- **未着手**: 顔の個体差（頭部係数 20 は設計書に数値がないため 0）、手指のポーズ、つま先、靴、
  肌の SSS、毛髪のカーブ化。設計書の参考画像は根拠にしない方針のまま。

### 8.6 素体以外を設計書から生成する（2026-09-22 追記）

MHR 素体の上に、05-woman 設計書の残りをコードで載せた。追加した汎用機能と、それぞれの判断。

- **`Strands` 形状**: 多数の `Sweep` をブーリアンなしで 1 メッシュに束ねる。髪束（束幅 2–15 mm、
  Fur の全頭利用を避ける、という設計書の指示）と靴紐に使う。殻の重なりは前提なので report は
  自己交差チェックを省き `overlapping` を記録する。`Sweep.up` を追加し、最初の断面フレームの基準方向を
  指定できるようにした（頭蓋の法線を渡すと平たい束が頭皮に沿う。既定の +Y は真下に落ちる経路で不定になる）。
- **髪**: 実測した頭部から楕円体を作り、生え際を方位角の関数（額 55°、耳上、うなじ 95°）で定義。
  前髪 13 束は額に沿って眉で止め、顔周り 4 束は肩の前へ、後ろ 64 束は 3 層（層ごとに 7 mm ずつ外側、
  下から生えて内層の下から出る）で肩の後ろへ落ちて毛先 0.66 m。束幅は方位間隔の約 2 倍にして頭皮を覆う。
- **ワンピース**: ロフト断面を実測胴断面 + 余裕 3 cm で作り、最上段を X 回りに 20° 傾けて前下がりの
  U ネックにする。胸元中央 120 mm に 12 本のギャザーを断面点の半径変調（振幅 4 mm → 2.5 mm → 0）で作る
  （「ギャザーは形状で作る」）。240 点の断面と 2 段しかないスカートは布がアコーディオン状に座屈したので、
  160 点 + smooth 細分化 1 + 8 cm ごとの環に変更して直った。布の四角形は正方形に近く保つ。
- **スニーカー**: 足の実測外形（足底の x/z 範囲、足首の断面）から底の丸長方形を押し出し、アッパーは
  内面としてロフトし `Solidify(offset=+1)` で外へ 6 mm 厚を付ける（内向きにすると足が突き抜ける）。
  靴紐は甲のラインを環の前端から補間して置く。全パーツ `parent_joint=<側>_subtalar`。身体とリグは
  底厚 25 mm 分持ち上げ、靴込み身長 1.625 m を満たす。
- **肌**: `Position` の積で箱マスクを作り、頬の赤み・目の下・唇・鼻周りの皮脂（粗さ低下）を層で重ねる。
  MHR の顔 UV は極小の島が多く、ベイクが触れないテクセルが黒く出た。ベイク画像をマゼンタで事前充填し、
  焼けなかったテクセルを焼けたテクセルの平均で埋めるようにして解消（全アセットに効く汎用修正）。
- **クリップ / QA**: 設計書の全 6 クリップ（idle, walk, turn, sit, raise-arms, physics-settle）と可動域
  確認ポーズ（膝 120°・肘 135°・股関節 90°・肩挙上 150°）、QA 静止画用の `face` / `neckline` / `sneaker`
  カメラ。sit と range_check のポーズはツイストボーン込みで破綻なく変形した。
- **未着手**: 眼球・歯（MHR LOD1 は閉じた一枚殻で、FBX にも別メッシュはない）、顔の個体差、指ポーズ、
  ランタイム物理（設計書の physics ブロック）、髪のカーブ書き出し。
